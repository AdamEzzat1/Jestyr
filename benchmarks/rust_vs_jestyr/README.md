# Rust vs Jestyr — ownership & safety benchmark suite

The research question:

> **For which ownership-heavy patterns does Jestyr express safe code with
> fewer concepts, fewer annotations, fewer escape hatches, or competitive
> performance compared with modern Rust?**

This is NOT "is Jestyr faster than Rust". Performance is one column;
expressiveness, annotation burden, escape-hatch count, and the shape of
each language's safety story are the others. The suite inherits the
twin-program discipline from `examples/cpp_compare/`: same algorithm, same
deterministic inputs, byte-identical output required before any timing row
is valid.

## Layout

| path | contents |
|---|---|
| `cases/` | one note per case: what ownership property it tests, status |
| `rust/std/<case>/` | Rust standard-library-only implementation |
| `rust/idiomatic/<case>/` | Rust + the crate a real user would pick (only where that changes the solution) |
| `jestyr/<case>.jtr` | Jestyr implementation (+ `<case>_rejected.jtr` where a rejection is part of the case) |
| `jestyr_std/<case>_std.jtr` | Jestyr + `examples/std` (`std/list` collections) where that changes the solution |
| `scripts/run_all.ps1` | build, verify byte-identical outputs, interleaved timing, emit results |
| `results/latest.{md,json}` | human- and machine-readable results (regenerated by the harness) |
| `results/ANALYSIS.md` | hand-written findings: annotation itemization, diagnostics, surprises |
| `METHODOLOGY.md` | exact definition of every metric; fairness rules |

## The two Rust tracks

- **rust-std** — standard library only: measures the core ownership model.
- **rust-idiomatic** — allows `slotmap`, `rayon`, `bumpalo`,
  `typed-arena`, … where a practicing Rust user would actually use one.
  Implemented only where the crate changes the solution; otherwise marked
  N/A (std already idiomatic).

Jestyr is compared against both. Jestyr is not penalized for lacking an
ecosystem; missing expressiveness IS documented (fairness rules in
`METHODOLOGY.md`).

## The two Jestyr tracks

- **jestyr** — the language alone: hand-rolled buffers (`alloc`+`slice`)
  and genref node graphs. What the FIRST pass measured.
- **jestyr-std** — the same cases restyled onto `examples/std` where a
  library changes the solution (today that means `std/list`): RAII-owned
  growable vectors, and for the two graph cases the rust-std INDEX shape
  (`List(Node)` + i64 links) that no container existed for before.
  Implemented only where std changes the solution; where the no-std twin
  already IS the std answer (case 3's `split_mut`, case 8's `par for`)
  the track is N/A rather than duplicated — those cases import std in
  their main track.

The jestyr vs jestyr-std pair on the graph cases (4, 5) prices the
CHECKED story (genrefs: per-node allocation + per-hop generation check,
stale handles fault deterministically) against the index story (no
checks, stale indices silently read reused slots — rust-std's safety
class) *within one language*.

## Running

```powershell
powershell -File scripts\run_all.ps1            # build + verify + time, writes results/
powershell -File scripts\check_rejections.ps1   # every rejection probe must refuse to compile
```

Prerequisites: stable Rust via rustup, gcc on PATH, and a release build of
the reference compiler (`cargo build --release` at the repo root). The
idiomatic track needs one `cargo` fetch of `slotmap` on first build.

## Current limitations

- Case 7's linear-capability half is design-only (safety-mosaic item 7
  unimplemented); it ships as two measured gap probes instead.
- Peak compiler memory (`scripts/measure_compiler_memory.ps1`, results
  in `results/compiler_memory.md`) covers rustc single-process and
  jestyrc-without-gcc — read the footnotes before comparing.
- Binary sizes compare an MSVC-linked Rust exe against a MinGW-linked C
  exe; reported raw, see METHODOLOGY for the caveat.
- Annotation counts are hand-itemized in `results/ANALYSIS.md`, not
  machine-counted.
